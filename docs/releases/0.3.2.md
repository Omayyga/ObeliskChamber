# Obelisk Chamber 0.3.2: the Memory Build

Everything since 0.3.1, including the test builds 0.3.1.1t and 0.3.1.2t.

Most of the work in 0.3.2 went into one problem: **the game using too much memory, and slowing down after an hour or so on PCs
with 16 GB of RAM or an 8 GB graphics card** (#126, #155, #162, #169). We added ways to measure where every part of the memory goes,
then cut the parts we could. The numbers are below.

**It isn't solved.** Memory use is much lower, and it grows more slowly, but video memory still grows over a long session.
[What's left](#whats-left) says where it still goes and what comes next. If you play long sessions on an 8 GB card, your logs
help most: see [Help us test](#help-us-test).

**Run Set up after updating.** The game code is built again (a lifter fix for a mod crash, and the new mod reading). Your saves
and settings carry over. The shaders aren't translated again.

## The memory numbers

Measured on a 16 GB laptop with an 8 GB card (i7-10870H, RTX 3070 Laptop) on the same route, 2 or 3 runs a side, with the
screenshots compared. Each change was measured on its own against the build before it, so the rows don't simply add up.

| | 0.3.1 | 0.3.2 | Change |
|---|---|---|---|
| Game heap counted against Windows' commit charge | 10,570 MiB | **3,817 MiB** | −6.6 GiB (#185, #190) |
| System RAM pinned for the GPU's small pools | 1,488 MiB | **740 MiB** | −0.75 GB (#185) |
| Pipelines built ahead at start | 4,465 | **800** | NVIDIA keeps about 1 MB of RAM for each (#179, #186) |
| RAM held by those pipelines | | | −660 MiB, then −250 MiB more (#179, #186) |
| The game's file cache budget | 4,768 MiB | **3,208 MiB** | levelled off at about 2.6 GB (#172, #176, #200) |
| Process working set | | | −0.5 to −0.7 GB (#185), about −0.25 GB more (#186) |
| Long hitches at loading screens (frames over 100 ms per run) | 5–9 | **0–1** | the memory census no longer stalls the game (#184) |

On **every** Windows PC, not just small ones, the game is now told it has 9 GiB as on the console (it was 10.5 GiB), and its heap
is committed as it's used rather than all at once. The game's own budgets don't change.

**From a player's PC** (#162, RTX 3070 Laptop, 4K output with DLSS Performance), a session of about an hour on 0.3.1 against the
first test build:

| | 0.3.1 | test build |
|---|---|---|
| 1% low in the last minutes | fell to **26.6** | 34–46 all session, no decline |
| Video memory in use | 6.0 GB (93–96% of the budget) from minute 52 | flat at about 5.4 GB from minute 30 |
| "95% of the OS budget" warnings | 2 | 0 |
| Pool copies at the end | 965 MiB | 706 MiB |

That run ended at 54 minutes, just before the point where 0.3.1 had slowed down. The memory had stopped growing well before
then, which is the better sign.

**Turned on by themselves on PCs with 20 GB of RAM or less, or a card with 8.5 GB or less** (`[memory] scale_limits = auto`; the
log's `memory limits:` line says whether it's on and why):
- The game's file cache is capped at the smaller of a quarter of your RAM and 40% of your card (`[fefw] file_cache_mb` sets it yourself).
- Smaller staging, texture-preparation and ASTC buffers.
- Pool copies in video memory that nothing read for 2 minutes are given back (`[nvn] pool_mirror_trim_idle_s`), and so are idle
  ones when memory nears the budget (`pool_mirror_evict_idle_s`).
- Textures nothing drew for 5 minutes are demoted, even below the pressure line (`[gfx] residency_trim_idle_s`).
- Only pipelines drawn in the last 3 sessions are built ahead (`[nvn] prewarm_budget`, `prewarm_promote_sessions`). The rest are
  built when first needed, or in the background into the pipeline cache (`[nvn] cache_rewarm`).
- Play pacing under memory pressure: new pool copies, texture transcoding and texture restores are spread across frames
  (#195). Under heavy pressure on the laptop, 1% lows rose 4–14% and frames over 25 ms fell from 7–10 to 2–4 per area.
- Video memory is taken from the driver in 32 MiB blocks instead of 256 MiB on 8 GB cards (`[gfx] video_block_mb`), so less
  of it sits empty inside them.

Every one of these has a switch in [runtime/docs/CONFIG.md](../../runtime/docs/CONFIG.md), next to the A/B result behind it.

## What's left

On a 74-minute session on the laptop, through many different areas, with no crashes:
- **Video memory still grows:** from 4.8 GB to about 6.9 GB. It stayed there when the session went back to an earlier area.
- **Most of that growth is empty space:** the allocator's free space inside its blocks rose from 9% to 31%, about 1.1 GB in 4,386
  gaps. Textures that are freed leave holes, and the driver only gets a block back once it is completely empty.
- **The game itself keeps about 580 more GPU pools** by the end. That part is the game's own.
- **Process memory** levelled off at about 6 GB, and reached 7.3 GB after the scene with the 1440p movie.

The next step, planned for 0.3.3, is to **defragment video memory at loading screens**: move live textures together, so whole
blocks empty out and go back to the driver. The 74 minutes were also one PC, and that session ran before the file cache cap
took effect (#200); on the dev PC a smaller file cache also cut video memory by about 0.5 GB. AMD's 8 GB cards (#155) haven't had a long session
with all of this yet.

## Fixes

- **Mod crash with the LOD mod** (#154): a hook placed inside a loop of the model-detail code lost registers when the game's code
  branched back into that loop. Fixed in the lifter.
- **Hair and cloth standing up at 60 and 120 fps** (#160): gravity and wind in the cloth step now scale so cloth settles where it
  does at 30 fps (`[fefw] cloth_gravity = match`).
- **Slow GPUs during big loads** (#126): the hand-off of texture transcoding to the CPU, and the per-frame cap, now go by a GPU's
  usual speed rather than its best pass. A GTX 970 never handed off before.
- **Shader cache saves could be lost:** new pipelines could miss a save, or be lost at exit, when the cache grew during the save.
  Cache files over 2 GiB now load.
- **Pipelines that ran out of memory** were skipped for the rest of the session. They are now built again 600 frames later,
  which is more likely to matter on 8 GB cards near their limit.
- **Two possible hangs fixed:** a lock-order deadlock between the heap and the write tracker, and a race between two resets of
  the same event.
- **Proton and Wine:** the memory guard, census and logs read 0 MB under Wine; they now read the right figure. The menu's
  Chinese font no longer shows `?`, and `[` can be bound to a key.
- **Fewer waits for the GPU on game threads** when the CPU touches a compute result (337 → 4 per route on the laptop), and
  14–20% fewer write faults on in-order copies (`[nvn] compute_out_fault_eager`, `[memory] write_watch_coalesce`).
- **Ultrawide:** the title screen's menu panel (#173), and the world map's icons, route dots and lines (#156), reach the screen edges.

## Mods

- **Exefs patches are read as EmblemWeave and fefw-recomp read them:** from subfolders, `.ips32` as well as `.ips`, and more
  `.pchtxt` forms (offsets with or without `0x` and of any length, `;` and `#` comments, `//` inside strings kept).
- EmblemWeave's two `npc_log` hook sites are in `main.sites`, so code mods made for it find them.
- The Io crash fix both upstreams build in stays an optional mod here (`patches/unitinfo_animal_crashfix`).

## Start-up and shaders

- **Fewer pipelines built at start** (above). The ones left out are built one at a time on an idle thread, into the pipeline cache.
- **NVIDIA's shader disk cache** is set to 10 GB for this game (`[gfx] nv_shader_cache_gb`), so driver updates and big games don't
  push out its compiled shaders.
- **The release runtime is built with a new profile** (profile-guided optimisation and ThinLTO) recorded on 0.3.2's code.

## For reports

- **Device-lost reports** name the first Vulkan call that failed and the last 64 compute dispatches (`[diag] dispatch_ring`).
  Technique from fefw-recomp #100.
- `[gfx] gpu_checkpoints = all` puts markers on copies, clears, barriers and queries as well as draws, and works on AMD too (#157).
- The load census gives the video memory allocator's own figures, a RAM census and the game's file cache.
- `[diag] soak_csv = soak.jsonl` writes memory gauges every 10 s for long sessions.

## Experimental, off by default

- **Decompiled lighting shader:** a box in Set up. It replaces the game's lighting shader with an edited one built from source.
- Native versions of the two hottest culling tests (`FEFW_HLE_CULL`), fewer barriers on copies and clears, and debug labels per
  render pass for GPU capture tools.

## Help us test

Post `ObeliskChamber.log` (the previous run is `ObeliskChamber.log.prev`), your GPU, RAM and driver version.

| You have | Try | What tells us |
|---|---|---|
| **An 8 GB card, AMD or NVIDIA**, that slowed down after an hour on 0.3.1 | A long session through several areas, with `[diag] soak_csv = soak.jsonl` in `ObeliskChamber.ini`. Post the log and `soak.jsonl`. | Whether video memory and the 1% lows hold over 60–90 minutes. |
| **16 GB of RAM or less** | Nothing to change. | The log's `memory limits:` and `file cache budget:` lines, and whether loads feel slower. |
| **Steam Deck / Linux** | Nothing to change. | The log's memory lines should no longer read 0 MB. |

## Known issues

- **Video memory still grows over long sessions.** See [What's left](#whats-left). Restarting the game clears it.
- **Radeon 8060S losing the device on the first frame** (#157) is still open.
- **HDR Native with frame generation** hasn't been tested together.
- **Switch plugins (`.nro` / `.nrr`)** can't run on any PC recomp of this game. Such a mod needs a version written as a Windows DLL.

## For builders and testers

- `make-release.ps1` warns when the runtime profile was recorded on older runtime code. Stamp a new profile with
  `python tools\perf\pgo_stamp.py C:\pgo\rt.profdata` (docs/PGO.md, "A release runtime").
- `[memory] test_ram_gb` and `[gfx] residency_test_budget_mb` pretend to be a smaller PC, for A/B runs.
- Routes can wait for the save to load (`@loaded`), and the A/B harness does a warm-up run, leaves out failed runs and compares pictures.
