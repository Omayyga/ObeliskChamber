# Obelisk Chamber 0.3.1

Everything since 0.3.0, including the test builds 0.3.1t to 0.3.4t.

**Update if you play on NVIDIA.** 0.3.1 fixes a GPU hang that ended in a "device lost" crash during battles on NVIDIA cards (#121,
reported again in #149). A handful of the game's shaders used an integer instruction that hangs NVIDIA's driver; they are now
translated without it.

**Run Set up after updating.** The shaders are translated again for that fix, and Set up rebuilds the game code. Your saves and
settings carry over. The first start after Set up prepares shaders again, so expect a longer first load.

> [!TIP]
> **Testers wanted.** Several changes in this release are switched off, or only act on some GPUs, until someone with that hardware
> has tried them. If you have one of the PCs below, please read [Help us test](#help-us-test) and post your log.

## Fixes

- **NVIDIA GPU hang in battle** (#121, #149): integer `abs` in the translated shaders is now written without the instruction that
  hung the driver. The device-lost report now also names the draw the GPU was on (`[gfx] gpu_checkpoints`), the driver's fault
  description where it gives one (`VK_EXT_device_fault`), and the build the report came from.
- **Slow GPUs losing the device on big loads** (#126, a GTX 970 after the Dagsion cutscene): on a GPU too slow for texture transcoding
  the work goes back to the CPU for the session, and transcoding is capped per frame, so a load no longer runs into Windows' 2-second
  GPU timeout. The device-lost report says when that timeout was the cause and what to change.
- **No false FREEZE report while starting**: the watchdog waits up to 60 s before the first frame (`[diag] watchdog_boot_seconds`).
  A slow disk or a big mod list was enough to trip it at 10 s.
- **GPUs without 64-bit floats** (Intel Arc and Iris Xe, #81): the game's auto-exposure shaders use doubles, which those GPUs can't
  run. They are now made 32-bit when they load (`[gfx] lower_float64`), and the log warns on such a GPU. See [Help us test](#help-us-test).
- **Frame generation in HDR** now gets the picture without the HUD, as in SDR: before, it could latch onto a small glare target.
- **The present waits for the frame's drawing** when the two are submitted apart (`[nvn] present_wait`), so a half-drawn frame can't
  be shown.
- **AMD: FSR 3.1 by default**, instead of FSR 4 on RDNA 2, which ran at a fraction of a frame a second and could crash AMD's driver.
  RDNA 4 still gets FSR 4 (`[upscale] fsr_version`).
- **Cutscene movies** decode on more threads, above normal priority, without a copy per frame, so 1440p movies keep up with their
  sound on CPUs with few cores.
- The overlay's line measurement and a few start-up paths had small bugs fixed along the way.

## Faster

Measured one change at a time on an i7-13700K with an RTX 3090 Ti, 3 runs a side on the same route, screenshots unchanged. The
gains overlap, so they don't simply add up.

- **The release runtime is now built with its profile** (profile-guided optimisation and ThinLTO), as the developer build always
  was. Earlier releases shipped without it.
- **Fewer GPU waits** (on NVIDIA):
  - small compute buffers the CPU rewrites every frame are read in place instead of copied in and out: GPU time −5.2% at 4K, 370 → 249
    full barriers a frame (`[nvn] compute_hot_host`);
  - back-to-back report writes share their barriers: GPU time −2.3%, 1% low +4.8% (`[nvn] batch_reports`);
  - render-pass conflicts and texture copies get exact barriers instead of full ones: GPU time −2%, full barriers 144 → 92 a frame
    (`[nvn] narrow_pass_conflicts`, `narrow_copy_barriers`). These are correct by the Vulkan spec on every GPU.
- **Less render-thread work** for the GPU memory copies: render thread −15% a frame at 720p / 240 fps, +6.8% fps there
  (`[nvn] mirror_lean`). This helps most where the CPU, not the GPU, is the limit.
- Smaller savings on the render thread: cloth without a system call per blend, a flat hook table, and cached alpha-test layouts.
- The log is written on a thread of its own, so the render thread doesn't wait for the disk.

## Enhancements

- **The title screen's cursor starts on Continue** when you have a save (`[fefw] title_continue`). With save slots, New Game is
  selectable too, and the cursor used to start there.
- **Mods window for code mods** (F8, `[gfx] mods_key`), also on the F1 menu's Mods tab for controllers. Code mods can add their own
  settings panels there (mod API version 5). The panels use the same interface as EmblemWeave's, so a panel mod works in both. The Mods
  tab and the F8 key only appear or act once a mod has added a panel, so a mod that uses F8 itself (such as the F8 Appearance Editor)
  isn't disturbed.
- **Set up and exefs mods:**
  - a mod whose patches can't be applied is left out with a note naming it, and the other mods still apply (before, one bad patch
    stopped Set up);
  - a patch may add code in the padding right after main's code ("code caves");
  - Set up keeps the old game files until the new build has linked, so a cancelled build doesn't break the game;
  - `.pchtxt` patch lines need an 8-digit offset, as in IPSwitch.
- **More in the log for reports:** the start-up line names the Windows power plan and the CPU's core types, a session summary
  (average, 1% and 0.1% lows, longest frame) is written every 5 minutes and at exit, and a `boot: timeline` line says where the
  start-up time goes.
- [docs/SETTINGS_GUIDE.md](../SETTINGS_GUIDE.md): a tip to set the NVIDIA app's Shader Cache Size to Driver Default or larger, so
  driver updates and big games don't push out this game's compiled shaders.

## Help us test

These are in 0.3.1 but switched off, or they only act on some GPUs. Each needs someone with the hardware to try it. Post
`ObeliskChamber.log` (it is overwritten at each start; the previous run is `ObeliskChamber.log.prev`), your GPU and driver version.

| You have | Try | What tells us it worked |
|---|---|---|
| **Intel Arc or Iris Xe** | Nothing to change: 0.3.1 makes the game's 64-bit shaders 32-bit by itself. If it still crashes, add `[setup] intel_shaders = true` to `ObeliskChamber.ini` and press Set up. | The log says `64-bit floats made 32-bit for this GPU`, and the game no longer loses the device. Please post on #81. |
| **AMD Radeon** | `[gfx] rt_no_storage = true` and `[gfx] image_format_lists = true` in `ObeliskChamber.ini` (these let AMD keep its colour compression) | Higher fps in the same spot, and no wrong colours or corrupted pictures. Screenshots help. |
| **AMD or Intel** | `[nvn] cs_ssbo_readonly = true`, `compute_shadow_min_bytes = 4096`, `shadow_lean = true` | Fewer copies between the CPU and GPU. No gain on NVIDIA; they may help where those copies cost more. |
| **A 4 to 8 GB graphics card** that slows down after long sessions or new areas | `[nvn] pool_mirror_evict_idle_s = 30` and `[gfx] residency_os_pressure = true` | The log's `pool copies: gave back ... idle chunk(s)` lines, and the frame rate holding up over a long session. |

## For builders and testers

- `fefw_rt.dll` is built with `C:\pgo\rt.profdata` and ThinLTO when the profile exists; `release_build.bat` warns when it doesn't.
- The A/B results behind each default are in [runtime/docs/CONFIG.md](../../runtime/docs/CONFIG.md), next to each key.
- Mod API version 5 (`runtime/include/nxrt/mod_api.h`): `add_panel`, `panel_visible` and `NxModUi`, laid out as in EmblemWeave. The
  member after `free_mem` is `open_list` here and `add_panel` there; the runtime tells the two calls apart, so mods for either work.
- Every A/B bat should set `NXRT_GFX_GPU_CHECKPOINTS=0`: the checkpoint key is in `[gfx]`.

## Known issues

- **HDR Native with frame generation** hasn't been tested together.
- **Cloth at 60 and 120 fps** is still a little stiffer than at 30.
- **Memory:** about 1 GB more than 0.2.2. With 16 GB of RAM this should be fine; if you run short, `[nvn] shader_pack_resident = false`
  gives back about 175 MB.
- **Switch plugins (`.nro` / `.nrr`, such as FEFW_RuntimePatcher)** can't run on any PC recomp of this game: the game's code is
  compiled ahead of time and nothing runs Switch code while playing. Such a mod needs a version written as a Windows DLL.
