# Obelisk Chamber 0.3.0

Everything since 0.2.2, including the two Intel test builds (0.2.3t and 0.2.4t).

**Run Set up after updating.** The game code is built differently in this release (faster translated code and the new frame-rate
fixes), so Set up builds it again, which takes a while. Your saves and settings carry over. The first start after Set up also
prepares shaders again, so expect a longer first load.

If you copied `ObeliskChamber.ini` from an Intel test build or a guide, remove the lines you added for testing: a key you set by
hand wins over the new defaults. [docs/SETTINGS_GUIDE.md](../SETTINGS_GUIDE.md) is new: it lists the settings worth changing and
who gains from changing them.

## Performance at a glance

The same PC, settings and save in all three: i7-13700K, RTX 3090 Ti, 4K output rendered at full 4K (no upscaling), 8192 shadows,
SDR, a 120 fps target, loading a save and playing on. One run each, so treat the numbers as a rough guide.

| | fefw-recomp 0.2.0 (the original) | Obelisk Chamber 0.2.2 | Obelisk Chamber 0.3.0 |
|---|---|---|---|
| Frame rate once settled | about 57 fps | about 79 fps | about 81 fps |
| Slowest 1% of frames once settled | 30 to 51 fps | 33 to 57 fps | 45 to 68 fps |
| Hitches during the run (total time) | 24 (8.5 s) | 22 (6.1 s) | 14 (2.6 s) |
| Hitches over 200 ms | 12 | 10 | 4 |
| Worst single frame | 1.8 s | 1.05 s | 0.59 s |
| Game running in slow motion while loading in | down to 0.50x | down to 0.60x | stays at 0.80x or above |
| Time until the area is loaded and smooth | 18.8 s | 15.1 s | 12.9 s |
| Placeholder textures on screen, longest | 2.4 s | 2.6 s | 1.5 s |
| Memory in use | 2.0 GB | 2.1 GB | 3.1 GB |

What changed in feel: loading into an area is shorter and smoother, with fewer and shorter hitches, and textures appear sooner.
Once settled, the frame rate is close to 0.2.2's. At native 4K this card is limited by the GPU (it is busy about 12 to 13 ms a
frame), so no CPU-side change can lift that. A lower render scale or an upscaler can. On PCs where the CPU is the limit, the
render-thread, game-code and CPU changes below matter more than they do here.

The differences between the runs: 0.2.0 and 0.2.2 ran with the 60 fps mode also on, and 0.3.0 adds the frame-rate fixes. 0.3.0
uses about 1 GB more memory, most likely the shader pack now kept in memory and the texture streaming buffers (not measured one by
one). In this run its first picture also came about 2 s later than 0.2.2's, most of it while DLSS (Streamline) started.

## Optimizations

**Loading and texture streaming** (from Stephen Jayakar's fork, plus our own tuning)
- Textures without their data yet are drawn with quick stand-ins while background jobs make the real ones. The render thread no
  longer reads the texture cache from disk or waits for a job. On his PC, the load-in frame after a menu went from 3.8 s to about
  0.3 s.
- An area's first texture uploads are spread over several frames, through one persistent upload buffer.
- For 3 seconds after a load, the GPU gives the texture queue more time each frame, so placeholder textures are replaced sooner
  (`[gfx] astc_gpu_load_ms`). On the test PC, placeholders after loads averaged 0.5 to 0.9 s instead of 1.6 s.
- The 140 to 500 ms gameplay hitches next to a memory import are gone: the pages are found from the heap's own table, not by asking
  Windows page by page.
- GPU memory chunks are prepared ahead on a worker instead of on the render thread when you arrive in an area.

**Render thread and GPU**
- The render thread's Vulkan calls are made by a second thread on CPUs with 6 or more cores (`[nvn] replay_threads`). On Stephen's
  PC the busiest street's render-thread work fell from 16.8 to about 14 ms a frame.
- Fewer GPU barriers: work that shares nothing runs side by side (his measurement: GPU time per frame 15.1 to 10.9 ms at 4K; ours
  about 8 % less).
- Draws re-check only the buffer slots that changed since the last check (about 0.2 ms less render thread a frame at 2,400 draws).
- The game's lighting shader uses the GPU's own float add instead of a retry loop.
- Vulkan objects are destroyed on a low-priority thread instead of the render thread.
- The camera data a runtime upscaler patches is kept in fast memory (51 to 114 fps in a test with a hand-set temporal mode).
- Optional, off by default: long frames sent to the GPU in parts (`[nvn] split_submit_ms`).

**Shaders**
- The whole shader pack stays in memory, so no shader file is read during play. Compute shaders are built ahead, and draws no
  longer wait for a shader still being built. On Stephen's PC with empty caches, the worst battle frame went from 142 to 44 ms.
- Background shader work steps aside when a frame runs late, so the game gets the cores during loads (`[nvn] compile_pace_ms`).
- Background build threads scale with the CPU and run below normal priority, on the efficiency cores where the CPU has them.

**Game code and CPU**
- Faster translated game code (Stephen Jayakar): condition flags and temporary registers kept in locals, native versions of the
  game's memory and string routines, the hottest code packed together, and the game's zstd decompression run natively. On his PC
  the game's main thread used about 25 % less CPU, and arrival frames after fast travel fell from 485 to about 320 ms.
- Polling loops re-read memory on every pass, so a translated loop can't hang waiting for a value that already changed.
- Less CPU spent between threads: per-thread counters, a cheaper starvation guard, and short spins before sleeping on CPUs with 8 or
  more cores (`[kernel] wait_spin`).
- The runtime (`fefw_rt.dll`) is built with a profile and ThinLTO. The game code stays a general build that runs on any supported
  CPU.

## For lower-end PCs

- **A Low graphics preset** that renders at half size per side, uses 1024 shadows and the console's handheld quality, and turns down
  the game's own reflections, ambient occlusion, crowd and scenery detail. Each can also be set on its own (`[fefw] reflections`,
  `ambient_occlusion`, `crowd_detail`, `scenery_detail`; they apply at the next start).
- **Defaults that fit small CPUs:** the render-thread worker, spin waits and early shader compiles only switch on where there are
  cores to spare (6 or more physical cores, 8 or more physical cores, and more than 8 threads), and background shader threads scale
  down.
- **Compatible build (CPUs without FMA3):** multiply-adds are done inline instead of through a slow library call. Savage Wind's
  similar change measured 130 to 151 fps.
- **RTX 20 and 30 cards with DLSS** use DLSS model E unless you pick one, which costs these cards much less GPU time than the newer
  default model (`[upscale] dlss_preset_auto`).
- **DLSS recovers** when a frame fails under video memory pressure: the built-in upscaler stands in, DLSS frees its memory and comes
  back about 2 s later, instead of staying off until restart. This mostly helps 6 and 8 GB cards.
- **Less CPU while loading:** the texture and shader changes above take the most work off the CPU, where small CPUs felt it most.
- If the seconds after a load feel slow on a weak GPU, `[gfx] astc_gpu_load_ms = 0` restores the old texture pace (placeholders then
  stay longer).

## Intel GPUs (Arc and integrated): please read

0.2.0 and 0.2.2 lost the GPU at or just after the title screen on Intel (issue #81). 0.3.0 includes the fix that the Intel test
builds checked:

- **`[gfx] intel_compat` turns on by itself on every Intel GPU**, discrete or integrated. It turns off the paths that lost the GPU in
  the upstream project's tests and ours: the lighter draw path (`[nvn] lean_draws`), texture residency (`[gfx] residency`) and
  three barrier shortcuts only ever tested on NVIDIA, and it uses full GPU barriers. The log says
  `GPU quirks: [gfx] intel_compat on`.
- **Shared memory imports are off on Intel** (`[nvn] pool_slabs = auto`), as in 0.1.7, which ran on the same driver.
- **A crash fix** for a write that landed just as memory was handed to the GPU. It was seen on an Arc B390 and could hit any GPU.
- **Tested:** an Arc B390 ran the 0.2.4t test build without the crash (30 to 40 fps at 20 W). We haven't heard back from the B580
  tester yet.
- **Start clean:** unzip into a new folder, and don't bring an `ObeliskChamber.ini` with lines from earlier test rounds. A line
  such as `lean_draws = true` wins over the Intel default and brings the crash back.
- **Expect it to be a little slower than on NVIDIA:** these paths were speed-ups. A few effects may look slightly wrong, because
  Intel can't run every fragment shader in the 32-wide groups the game was written for. That isn't the crash; screenshots help.
- XeSS works on any GPU and runs best on Arc. See the README for the file it needs.

If it still crashes, please post `ObeliskChamber.log`, any `*_crash.txt`, your GPU model and driver version on #81.

## Enhancements and quality of life

**Graphics and settings**
- **Graphics presets** (Low / Medium / High / Ultra) in the launcher, the F1 menu and Recomp Options. Medium is the console's
  picture. Each surface shows Custom when your settings match no preset.
- **Live settings:** the preset, render scale, fixed render size, shadows, quality, frame rate, dynamic resolution, upscaler and
  upscaler tuning, audio device and a few log switches apply at once from the F1 menu and Recomp Options. The menus say which
  settings still need a restart, and why.
- **The game's own HDR** (`[hdr] mode = native`): the game is told the display is HDR, as on a Switch 2 with an HDR TV, and its own
  10-bit HDR picture goes to the screen unchanged. The game's Brightness options work. If you had Native saved before, you get the
  new behaviour; Auto and On still convert the SDR picture as before.

**Frame rate**
- **Frame-rate fixes** (`[fefw] frame_fixes`, on): at 60 and 120 fps, systems made for 30 fps keep their real speed. Before, capes
  and hair, physics, cutscene camera shake, animation eases, map markers, menu timers and dialogue typing ran 2x fast at 60 and 4x
  at 120. It's live in F1 and on the + menu's Frame Rate page.

**Menus**
- **Quit Game** under **+ > System**, after Return to Title. It asks in the game's own yes / no dialog ("Quit the game?", the cursor
  on No) in every game language, then closes the game the same way as F1's Quit game.
- **The F1 menu no longer dims the game**, so filter, HDR and picture settings can be judged while you change them. Move it by
  dragging it with the mouse or with the right stick.
- **The F1 Debug page** shows the CPU next to the GPU.
- Recomp Options redraws its rows after a preset change, so Render Scale, Shadow Resolution and Quality show their new values.
- F1 and the launcher's Quality lists gain Handheld, and the launcher's Render scale and Upscaling tier now move together.

**Ultrawide**
- **Output lists grouped by shape** (16:9, 21:9, 32:9) with 3840x1600, 5120x2160 and 3840x1080 added, and a "This monitor" entry. Notes
  under the rows say when the output and the monitor don't match.
- **Full-screen pictures keep their shape** on wide outputs (`[fefw] ultrawide_images` = `fill`, `fit` or `stretch`): the title
  screen, loading screens and story illustrations.
- The title screen's side picture and the world map's art stay in the 16:9 area, and the world map's dark route outline is now
  squeezed like the routes (#66).

## Fixes

- **No black models after loading:** models on screen no longer show the black placeholder for a split second after every load.
- **Blocky clouds** in the sky are smooth again.
- **Save list:** after saving to a new slot, the list no longer opens a second save prompt and leaves the save window on screen,
  which also stopped the camera from turning.
- **The game's temporal upscaler settings in `controls.ini`** (`[upscale] mode` = fsr3, dlss, dlaa or xess) are now ignored with a
  log line. Fortune's Weave upscales its own scene, so they ran a second upscaler on top. Use F1 > Upscaler instead.
- **Integer textures** get the unfiltered sampler Vulkan requires (a validation error at the title screen).
- **A possible hang removed:** the game's statistics counters are written every time again (`[nvn] stat_counters = always`).
- Button prompt fonts are read through the game's RomFS, so a packed `.nup` and RomFS mods work.

## Mods and the launcher

- From a source checkout, the launcher now notices when an installed mod brings new hook sites and lifts them at Set up (contributed
  by ranbinrang-rgb). Release packages already did this; the check is now also keyed on the mods' files, so installing or updating a
  code mod while the launcher is open is noticed.
- The launcher no longer crashes when its library folder has a name that isn't valid Unicode.

## For builders and testers

- **Repeatable performance runs:** scripted routes that play the same thing every time, a recorder that turns your own play into a
  route, an A/B runner and a report ([docs/PERF_ROUTES.md](../PERF_ROUTES.md)).
- **Runtime profile for releases:** `fefw_rt.dll` can be built with a profile and ThinLTO (`NX_RT_FLAGS`, [docs/PGO.md](../PGO.md));
  `tools/perf/pgo_stamp.py` records what a profile was trained on and the release script warns when it's out of date.
- New measuring keys: `[prof] gpu_stats`, `[prof] hitch_ms`, `[nvn] out_prog_ab` and `[nvn] rt_check` (testing only: it costs 15 to
  25 fps).
- The lifted code builds at `/O2` by default in CMake builds.
- All 174 runtime test groups pass again.

## Known issues

- **Memory:** about 1 GB more than 0.2.2 (3.1 GB in our run). With 16 GB of RAM this should be fine; if you run short,
  `[nvn] shader_pack_resident = false` gives back about 175 MB.
- **Cloth at 60 and 120 fps** is still a little stiffer than at 30.
- **AMD:** the tracked GPU barriers are on for AMD but have only been tested on NVIDIA. If you see a corrupted picture, try
  `[nvn] dispatch_barriers = full` and `game_barriers = full`, and please report it.
- **HDR Native** hasn't been tested with FSR 1, NIS or frame generation.
- **Slow disks:** the log can show a watchdog "FREEZE" line before the first frame while the game's files are indexed. The game goes
  on; it isn't a hang.
- **Intel:** see the section above (possible small visual glitches; B580 not yet confirmed).
